# Testing

`make test` requires Bash, Python 3.11+, `tar`, and the standard system utilities used by Anvil. It makes no external OpenCode, Databricks, or model calls. Local OpenCode 1/2 fixtures and a fake Databricks CLI validate runtime and adapter contracts. The entire suite runs with temporary HOME and XDG roots, a constrained PATH, no Python user site, and cleared external Databricks selectors. Communication and artifact regressions use the Python standard library and local fixtures. Windows users can run the suite under WSL.

## Offline runtime and configuration checks

OpenCode fixtures validate the supported OpenCode 1.18.18 and 2.0.0 profile shapes, config loading, agent/command/skill discovery, plugin/Reference behavior, and runtime-specific capabilities. These are adapter contract fixtures, not real OpenCode binaries. The suite audits generated OpenCode 1 and 2 config, checks model neutrality, single-agent policy, denied subagents, empty MCP defaults, plugin scope, and scans text files for accidental secret signatures.

## Databricks checks

`tests/fixtures/bin/databricks` returns deterministic Anvil profile, identity, cluster/warehouse, execution, permission, and system-table responses. Tests cover clean Anvil-owned profile creation, external profile isolation, legacy state migration, auth strategy selection, secure config/state persistence, environment isolation, resource selection, stopped-resource approval, command context cleanup, timeout cancellation, SQL state/result bounds, mutation rejection, system-schema discovery, FinOps evidence cases, and query recipe contracts. Fixture logs contain endpoint names and bounded request metadata without Python source, SQL text, credentials, or result payloads.

No fixture contacts a real Databricks workspace. Passing these tests validates the adapter's offline behavior and API request/response contract, not a live connection.

## Memory, source, and lifecycle checks

V1-format Markdown fixtures are searched with `PATH` deliberately lacking `rg`; tests verify the original file hash remains unchanged. Memory tests cover validation, status/confidence/aliases, accent-insensitive multilingual retrieval, bounded results, explicit writes, provenance, duplicates, source freshness warnings, and no-write search behavior. `/distill` fixtures cover documentation/code/test corroboration, stale docs versus active behavior, unreferenced legacy code, policy/implementation conflicts, historical claims, source drift, idempotency, and unavailable images.

Lifecycle checks use local OpenCode wrappers and isolated HOME/XDG trees. They cover the fresh-repository public command matrix before and after reforge, partial/corrupt lifecycle states, missing memory, offline runtime-operation blockers, rollback guidance with no snapshot, repeated reforge, Anvil upgrade preserving both OpenCode generations, dry runs, explicit runtime migration, verified rollback, provider conversion, opaque data/state restoration, and memory preservation. A brownfield 2.6.1 fixture includes an unrecorded legacy manifest, a 1.19.3 runtime, existing memory, Anvil-owned Databricks profile/state, a verified rollback snapshot, and a realistic `node_modules/.bin` tree with valid and broken links. It exercises inspect, doctor, read-only upgrade planning, real upgrade, manifest ownership, runtime/memory/provider preservation, and reforge. Adversarial cases verify that escaping and broken symlinks at manifest-owned skill/command paths remain corruption and that doctor recommends reforge only when it can safely run; an untrusted `opencode.jsonc` symlink receives no automatic reforge recommendation. Failure injection covers candidate validation, rehearsal, backup creation, failures before mutation and metadata commit, hard interruption after config rename, post-config failure, and doctor failure after upgrade. The audit also adds source-to-target ownership/collision cases, preservation of disabled V1/V2 user agents, spaced/Unicode HOME/XDG paths across Anvil upgrade/reforge/runtime update from an external `make -C` caller, concurrent lifecycle calls, and a read-only config-parent preflight. Databricks tests simulate missing pip and a venv interpreter symlink, and exercise safe phase diagnostics through the real SDK worker subprocess boundary.

## Release, harness, and stats checks

The suite checks shell/Python syntax, runtime policy and capabilities, release documentation, the global harness budget and required invariants, skill use/do-not-use descriptions, query recipe constraints, combined JSON runtime/Databricks/communication/analysis capabilities, and the absence of the standalone legacy organization token in tracked or untracked repository text. The stats formatter is checked with a structured local fixture.

## Intent and analytical intelligence checks

`tests/analysis.py` covers exact original-request provenance, explicit/derived requirement separation, semantic references/confidence, FAST/STANDARD/DEEP budgets, supported table formats, symlink/size/row/output limits, source-hash drift, deterministic primitives, units and percentage points, trend evidence thresholds, distribution versus mean, cohort population changes and like-for-like comparison, eligible-population coverage, correlation wording, evidence references, Pareto materiality tiers, artifact adaptation, and transfer to an unrelated helpdesk dataset. It records a local 10,000-row profile-plus-grouped-operation runtime. The lifecycle suite verifies that a 2.6.1 source upgrade installs and manifests the new helper and that the installed helper profiles a named local fixture. These tests use no model, external service, or persistent state; they cannot validate live semantic judgments or model responsiveness.

## Communication and artifact checks

`tests/communication.py` validates Decimal deltas, percentage points, zero/near-zero/negative baselines, normalization, distribution percentiles/outliers/missing values, explicit exclusions, projection classification and assumptions, audience policy, ranking semantics, exact slide counts/roles, evidence ID integrity, and recomputation of plan metrics. Local text, CSV, JSON, DOCX, PPTX, XLSX, symlink, size-limit, and optional-PDF-unavailable fixtures cover bounded input behavior. Markdown output checks exact slide counts, citations, permissions, no-overwrite defaults, and reviewer findings. SVG checks XML accessibility, model-backed review, boundary containment, and the regression where an edge crosses an unrelated node. None of these tests requires a model, OpenCode 2 feature, Databricks workspace, or network access.

## Limits

The suite does not run a real model, contact a Databricks workspace, authenticate with a provider, or smoke-test live OpenCode release artifacts. Runtime install/upgrade still needs access to the official release source and verifies its published artifact digest. OpenCode database files remain opaque; Anvil does not inspect or edit undocumented SQLite schemas. Semantic distillation quality remains agent-guided and is not represented as benchmarked model behavior. The [system map](system-map.md) and [full-system quality audit](quality-audit.md) document the current component inventory, confidence matrix, findings and evidence limits.

## Engineering continuity checks

`tests/engineering.py` exercises direct-task bypass when repository counts are large, explicit risk-trigger escalation, separate model validation, task/milestone/project criteria, combined dependency cycles, verified versus implemented status, semantic UNKNOWN gates, scope authorization, atomic/checksummed generations, compare-and-swap races, command serialization, hard interruption, explicit recovery, stale source/specification detection, selective invariant invalidation, milestone-scoped checkpoints, selective replan, bounded checks, symlink/security constraints and installed helper use on both profiles. `evals/engineering/adaptive.py` compares 18 paired task-local activation cases against the prior 2.9 signal thresholds. `evals/engineering/run.py` adds repeatable ingestion and unrelated scheduler protocol replays, partial milestone interruption, compaction/history loss, full coverage, measured state writes and architecture-evaluation counts, and injected boundary-leak detection. Mandatory checks are offline.

Eight system-design and 13 Spark cases provide explicit substantive rubrics; `review_cases.py` keeps structural checks separate from attributed semantic judgment. See [engineering methodology](engineering-evaluation.md) for baseline/candidate observations and optional live-model limitations. Deterministic route and protocol replay are not autonomous LLM benchmarks. OpenCode runtime/config integration is unchanged from 2.9; this release uses the local V1/V2 profile fixtures and makes no new native-runtime validation claim.
