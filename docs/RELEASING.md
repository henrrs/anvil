# Releasing Anvil

Anvil uses Semantic Versioning. Anvil 2.0 was the runtime/configuration migration to OpenCode 2. Starting with Anvil 2.1, Anvil product versions and OpenCode runtime majors are independent; runtime-major migration is explicit. Anvil 2.3 adds Databricks provider independence; 2.3.1 corrects runtime independence; 2.4.0 adds safe runtime quiescing and topology-aware setup; 2.5.0 moves Databricks onboarding to an Anvil-owned config and profile. Anvil 2.6.0 is a MINOR release because it formalizes readiness as a persisted, validated runtime contract and advances the provider state schema while preserving command compatibility and lazy legacy migration. Anvil 2.6.1 fixes provider fallback provisioning and persisted SDK executable reuse. Anvil 2.6.2 is a PATCH release: it hardens lifecycle reporting, offline test isolation, and SDK setup/diagnostic handling without changing the Databricks state schema or readiness contract. Anvil 2.7.0 is a MINOR release adding backward-compatible, runtime-independent evidence-backed communication and artifact capabilities without a persistent-data migration. Anvil 2.7.1 is a PATCH release restoring installed-profile compatibility during lifecycle audits. Anvil 2.8.0 adds a managed-config manifest and durable recovery; 2.9.0 adds optional long-horizon engineering continuity; 2.10.0 adds task-local adaptive activation and scoped architecture evidence; 2.11.0 extends the communication plan; 2.12.0 refines lazy editorial guidance and shared-config ownership-aware lifecycle preservation; 2.14.0 realigns analytical architecture; 2.15.0 is a MINOR release for additive semantic evidence and certification without changing persisted state or runtime policy.

## Version bumps

- **PATCH** fixes a bug without an intended behavior or data-format change.
- **MINOR** adds backward-compatible behavior or capabilities.
- **MAJOR** changes a breaking product, lifecycle, or persistent-data contract.
- OpenCode runtime support additions or runtime policy changes are released according to their Anvil compatibility impact; never infer a required OpenCode major from the Anvil version.

## Release checklist

1. Update `VERSION`.
2. Add the release to `CHANGELOG.md`.
3. Add or update `docs/versions/vN.md`; a separately documented patch may use `docs/versions/vN.N.N.md`. Update the capability matrix and [runtime compatibility](runtime-compatibility.md).
4. Add migration instructions when config, runtime policy, backup, rollback, or persistent data behavior changes.
5. Update relevant ADRs when runtime adapters, capabilities, or lifecycle semantics change.
6. Recheck current official OpenCode 1 and 2 compatibility and update `docs/opencode-compatibility.md`.
7. Run `make test`; the mandatory suite must remain offline and includes OpenCode 1/2 and Databricks fixtures plus isolated upgrade and rollback lifecycle checks.
8. If a release claim requires live OpenCode or Databricks compatibility, run and record a separate authorized smoke check; never describe fixture validation as a live service test.
9. Verify that the implementation, tests, compatibility document, changelog, version history, and capability matrix agree.
10. Verify that public command text and JSON output remain separate, setup authentication choices are topology-aware, and `make upgrade DRY_RUN=1` does not signal or write live state.

The `make test` suite includes deterministic provider, install-double, PATH, SDK fallback, VS Code discovery, state-security, dry-run, version-documentation, harness, query-recipe, FinOps, runtime-independence, credential-boundary, and repository-hygiene checks. It denies external socket connections during local lifecycle tests while allowing loopback for isolated runtime fixtures. It rejects a `VERSION` without matching changelog, version, capability, compatibility, and migration documentation. It does not resolve external runtime releases or contact a Databricks workspace.

## Anvil 2.9–2.12 engineering gates

Anvil 2.9 adds optional task state and progressive skills; 2.10 governs activation without weakening those guarantees. 2.11–2.12 extend renderer-independent analytical/editorial/visual communication; 2.12 also refines local config ownership and rollback. Run engineering unit/fault/concurrency/compaction tests, paired adaptive-route cases, communication audience/epistemic/visual fixtures, and lifecycle isolation with plugin/MCP/unknown-config changes and post-snapshot rollback edits through `make test`. Keep model/semantic and live latency results explicitly unmeasured unless a live harness and rubric adjudication actually ran. Preserve the local-task state bypass and permanent-kernel budget. Verify older source profiles, separate XDG task-store preservation, managed inventory, selectively invalidated evidence, private scoped snapshots and the six-prior-minor migration window. The 2.12 candidate remains **NOT READY** until the real Anvil presentation benchmark and live-model responsiveness comparison are reviewed.

## Anvil 2.14 analytical intelligence gates

For the 2.14 candidate, verify the analysis-to-communication dependency direction, candidate-only semantic profile confidence, observation versus entity cardinality, composite-grain and repeated entity-period regressions, population/cohort and contribution evidence, descriptive composition-share changes and claim checks, scope-aligned coverage validation, and profile/source-hash reuse. Run communication regressions and the full isolated lifecycle suite to reconfirm managed package installation, both runtime profiles, and preservation of user-owned config. Review the recorded synthetic baseline/candidate timing and treat its single-fixture regression as a finding, not proof of acceptable product latency. Do not claim that candidate metric questions implement autonomous hypothesis investigation, exact composition decomposition, anomaly detection, live model quality, or cost improvement. The 2.14 candidate is **NOT READY** until the required live-model claim/semantic quality, end-to-end latency/token cost, and analytical/artifact review evidence are available.

The 2.14 analytical evidence gate is implemented by `make eval-analytical`, `make eval-analytical-model MODEL=provider/model RUNS=N`, and `make eval-analytical-full`. Run the deterministic harness offline, inspect L1 and L2 separately, and review fixture/scoring changes before creating the immutable baseline with `make eval-analytical-baseline`. Model runs are opt-in and may send the named dataset to the selected provider. Apply structured human review to model results and preserve the private run artifacts. Verify that the blind workspace excludes hidden truth and the repository and that unavailable model evidence is shown as blocked or not measured. A passing deterministic harness is not model-quality or rendered-presentation evidence. Keep 2.14 **NOT READY** until blind runs and human review establish L3–L5 and quality/cost acceptability.

## Anvil 2.15 semantic foundation gates

Run `make eval-analytical-semantic` after `make eval-analytical`. Confirm the immutable 2.14 baseline hash is unchanged, all known L1/L2 checks remain 100%, the 24-case fixture snapshot matches its deterministic generator, composite entity/grain cases pass, high-confidence entity precision has no false positives, and ambiguous inputs abstain. Review confidence by level, the role/event/time checks, all metamorphic transformations, evaluator mutations, metadata/lexical ablations, sample-size/cardinality/temporal-density sensitivity, and FAST/STANDARD/DEEP timings beside the frozen 2.14 performance. The deterministic gate may report **READY_FOR_MODEL_EVALUATION**; this means only that the semantic foundation is ready for a separate blind L3–L5 model run. It does not establish model quality or make the overall 2.15 candidate release ready. Keep the overall candidate **NOT READY** until model-backed quality/cost and human communication review are completed.
