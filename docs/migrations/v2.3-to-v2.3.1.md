# Anvil 2.3 to 2.3.1 migration

Anvil 2.3.1 corrects runtime lifecycle independence. The release keeps the Anvil 2.3 feature set and supports the same OpenCode 1.x/2.x versions.

## Upgrade Anvil offline

After obtaining the repository update locally:

```bash
make test
make doctor
make upgrade DRY_RUN=1
make upgrade
make doctor
```

`make upgrade` uses the validated local OpenCode executable, reports `Network required NO`, and preserves the exact runtime version and executable. It makes an Anvil-scoped backup and does not change OpenCode config, binary, data, state, or `PATH`. The dry run creates no backup and changes no files.

An HTTP 403 from an OpenCode release endpoint no longer blocks this Anvil upgrade. It matters only when an explicit runtime operation needs upstream release data.

## OpenCode runtime operations

```bash
# Update OpenCode within its current major
make update-runtime DRY_RUN=1
make update-runtime

# Change major only when explicitly approved
make migrate-runtime OPENCODE_MAJOR=2 DRY_RUN=1
make migrate-runtime OPENCODE_MAJOR=2
```

Both runtime operations may need access to official release services. They validate and rehearse the candidate, create a runtime-scoped snapshot before mutation, and roll back on postflight failure. A same-major update preserves the Anvil release/config. A major migration also changes the Anvil runtime adapter.

`make reforge` reuses an existing healthy supported OpenCode runtime. A clean first installation may resolve and download the runtime selected by local policy.

## Rollback

`make rollback` follows the selected backup's recorded scope. An Anvil-only snapshot restores Anvil config and metadata while preserving the exact OpenCode runtime/data/state. A runtime-scoped snapshot can restore the previous OpenCode runtime/config/data/state. Current Markdown memory remains in place and is archived separately before rollback.

See [Anvil 2.3.1 release notes](../versions/v2.3.1.md) and [runtime compatibility](../runtime-compatibility.md).
