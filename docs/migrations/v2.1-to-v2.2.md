# Anvil 2.1 to 2.2 migration

Anvil 2.2 adds optional Databricks integration and a smaller execution-focused harness. It preserves the selected OpenCode major, existing Markdown memory, source registry, and the upgrade/rollback lifecycle.

## Upgrade Anvil

Review the staged upgrade and run it:

```bash
make inspect
make upgrade DRY_RUN=1
make upgrade
make doctor
make capabilities
```

`make upgrade` keeps OpenCode 1 on OpenCode 1 and OpenCode 2 on OpenCode 2. Databricks is optional; Anvil installs and remains usable if its CLI or authentication is unavailable. The terminal installer may offer profile setup after a successful upgrade. Declining it does not affect Anvil setup.

## Configure Databricks

Install the official Databricks CLI through the approved workstation path. Anvil supports CLI 1.0.0 or newer and does not replace an existing managed CLI. Authenticate through the CLI, then select the Anvil default profile:

```bash
databricks auth login
make databricks-setup
```

One valid workspace profile can be selected automatically. Several profiles require an explicit choice. The selected name and workspace host persist in a private Anvil preferences file; the CLI continues to own credentials. An invalid selected profile must be repaired directly, and Anvil will not silently switch workspaces.

`make doctor` reports optional Databricks state. `make capabilities` includes both runtime and Databricks state in text or JSON. Neither starts compute. Use the `anvil-databricks` skill for requested Python/SQL execution, live system-table discovery, and evidence-based FinOps analysis.

## Runtime and rollback

The Databricks capability is shared by both supported runtime profiles. No OpenCode major migration, plugin enablement, or MCP configuration is needed. Use `make migrate-runtime OPENCODE_MAJOR=N` only for a separately approved runtime-major change.

`make rollback` restores the latest verified OpenCode config/runtime/data/state backup. Anvil's Databricks CLI profile and `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks.json` preferences live outside that managed tree and are not overwritten by upgrade or rollback. Existing explicit Markdown memory and knowledge retain their current separate data paths.
