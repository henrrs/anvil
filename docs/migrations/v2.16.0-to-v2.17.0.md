# Anvil 2.16.0 → 2.17.0 migration

Anvil 2.17.0 converges the Analytics runtime for existing installs. It keeps the current OpenCode major unless you explicitly run a runtime update or migration.

The same-major source window retains the supported Anvil 2.6.x line through this release.

If `make inspect` reports `RECOVERABLE`, a manifest-owned regular file differs from the installed checksum and this release has a matching hash-pinned replacement. `make doctor` recommends `make upgrade`; it does not require `make reforge`. Review `make upgrade DRY_RUN=1` for the installed/target releases, path, ownership and safe hashes. The real upgrade preserves the exact current file in its rollback snapshot before replacement. A missing target artifact, invalid checksum/manifest, symlink or ambiguous ownership remains blocked for manual review.

The repository checkout and installed Anvil files are separate state. `git pull` updates the source checkout; it does not change the installed config. The release artifact hashes in `config/managed-inventory.json` validate the staged target before it can repair installed drift.

If an existing user-owned file already occupies a newly introduced Anvil path, the upgrade preserves it without changing ownership when it is a regular file with bytes identical to the verified target artifact. A differing file or filesystem node remains a blocking collision so user content is not replaced implicitly.

## Preview and upgrade

```bash
make upgrade DRY_RUN=1
make upgrade
make inspect
make doctor
make capabilities
make analytics-status
```

The dry run lists the managed file plan, pinned Analytics packages, runtime artifacts, service activation, OpenCode/canonical-session bootstrap and background metadata hydration. It makes no filesystem, dependency, systemd, runtime or catalog changes.

During a real upgrade, Anvil prepares DuckDB and PyArrow in a private release-pinned Python environment before switching the managed config. It installs the Analytics version/runtime policy/dependency lock, syncs and verifies the service, starts or recovers the OpenCode runtime and canonical Analytics session, then begins background metadata refresh. Existing Analytics SQLite/workspace/Parquet state is not copied into managed-config backups. If dependencies or readiness cannot be established, the lifecycle reports the blocker and uses its verified rollback path; it does not report success.

If the package source is unavailable on a company network, configure the supported pip proxy/package mirror in the shell or pip configuration used by Anvil, then rerun `make upgrade`. The failure occurs before config activation if required packages cannot be installed and validated. Do not run `pip install` into system or shell Python.

## Normal use

`make analytics` reuses or starts the managed service and prints `Anvil Analytics READY` and its URL. No manual service start or session setup is needed. Use `make analytics-dev` only for a foreground development server. A selected STOPPED warehouse starts only when the query route resolves to remote Databricks SQL. Catalog metadata refreshes in the background; cached results are visible first and table rows remain lazy.

`make update-runtime` updates OpenCode within its current major, then revalidates Analytics. `make migrate-runtime OPENCODE_MAJOR=N` prepares the matching adapter/dependencies, installs the target executable, and only then activates the service. Neither command is needed for an Anvil-only upgrade.

## Recovery and rollback

If inspect/doctor reports a dependency, service or canonical-session blocker, read its reason and rerun `make upgrade` after the network/runtime condition is fixed. Rollback restores the managed Anvil/OpenCode profile scope recorded in the snapshot, including the exact pre-upgrade bytes of a drifted managed file, and preserves Analytics user data. `make reforge` remains available for explicit rebuild/recovery; it is not required for verified repairable drift. The [Analytics operations guide](../analytics-workspace-operations.md) covers service, metadata and warehouse states.
