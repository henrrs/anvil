# Migrating from Anvil 2.5.0 to 2.6.0

Anvil 2.6.0 changes Databricks readiness reporting and provider-state metadata. It does not change the Anvil-owned profile location, authentication storage, or OpenCode runtime.

## Apply the Anvil release

```bash
git pull
make test
make upgrade
make doctor
make capabilities
```

`make upgrade` updates Anvil while preserving the exact validated OpenCode executable/version. It does not install a Databricks client or change Databricks credentials.

## What changed

When an Anvil-owned Databricks profile already exists, `make doctor` now performs read-only workspace validation through current-user, cluster-list, and warehouse-list operations. If the profile is not configured, doctor stays local and reports `NOT_CONFIGURED`. Doctor never starts compute or opens interactive authentication; use `make databricks-setup` when a sign-in repair is needed.

`make capabilities` remains local. It reports provider support and availability separately from recent verification. Cached verification becomes stale after 15 minutes, so run `make doctor` to refresh it.

Provider state schema 3 is migrated lazily when read or saved. No credentials are copied or rewritten. Existing workspace config remains at `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks/databrickscfg`.

If doctor reports a CLI timeout, shared network failure, invalid authentication, or permission blocker, the state records that category. Provider-specific CLI failures may use the isolated SDK; shared authentication and network failures stop without cycling providers. Empty cluster or warehouse lists are successful readiness evidence, and setup does not require running compute or SQL access.

Anvil 2.6.0 retains OpenCode 1 and 2 support. `make update-runtime` and `make migrate-runtime OPENCODE_MAJOR=N` remain explicit runtime operations; this Anvil upgrade does not move the installed OpenCode major.
