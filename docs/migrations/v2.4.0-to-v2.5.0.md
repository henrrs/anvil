# Migrating from Anvil 2.4.0 to 2.5.0

Anvil 2.5.0 changes only Databricks configuration ownership and onboarding. It does not upgrade or migrate the OpenCode runtime.

## What changes

Earlier Anvil setup could select a profile from the general Databricks config. Anvil 2.5.0 creates its own profile in `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks/databrickscfg`, usually `anvil-dev`. Existing profiles such as `DEFAULT` or `dev` stay available to their original tools and are not renamed, edited, copied, deleted, or reauthenticated by Anvil.

Legacy Anvil state that contains `selected_profile = dev` is not treated as ownership. Setup may show the stored workspace host as a suggestion and asks the user to confirm it. No credential is copied from an external profile or cloud credential store. The first Anvil-owned setup may therefore require a clean sign-in; later setup revalidates the Anvil profile and reuses its supported authentication.

## Upgrade and setup

```bash
git pull
make test
make doctor
make databricks-setup DRY_RUN=1
make databricks-setup
make doctor
make capabilities
```

If you do not use Anvil's Databricks capability, no Databricks setup action is needed. For a user who already uses Databricks through Anvil, run the setup command and confirm the saved workspace host or enter the intended workspace URL. The default environment is development and creates `anvil-dev`.

`make databricks-setup RESET=1` is only for replacing an Anvil-owned config. Anvil validates a staged replacement first, then keeps a private backup and changes only its own `databrickscfg`. It does not clear an Azure CLI session or modify `~/.databrickscfg`. If setup reports ambiguous ownership, stop and inspect `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks/databrickscfg`; reset does not authorize overwriting data whose ownership is unknown.

Doctor reports how many external profiles it detected and always says that Anvil does not use them. Anvil strips inherited `DATABRICKS_*` overrides from its child processes and shows variable names only. The parent shell environment remains unchanged.

## Runtime and rollback

Anvil 2.5.0 supports both OpenCode 1.x and 2.x. `make upgrade` updates Anvil while preserving the exact validated OpenCode runtime; it does not perform Databricks authentication. `make update-runtime` and `make migrate-runtime OPENCODE_MAJOR=N` remain explicit operations. An Anvil rollback restores Anvil metadata according to backup scope; the separately owned Databricks config and credential stores are not deleted by rollback.

For operational details, see [Databricks setup](../databricks/setup.md), [authentication](../databricks/authentication.md), and [security boundaries](../databricks/security.md).
