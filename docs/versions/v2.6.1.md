# Anvil 2.6.1

Anvil 2.6.1 corrects Databricks provider fallback and clean-session SDK execution while preserving the schema-3 readiness contract introduced in 2.6.0.

## Databricks provider recovery

An installed CLI binary is not treated as proof that the CLI can complete workspace requests. During the explicit `make databricks-setup` flow, a provider-specific CLI health failure can trigger installation of Anvil's isolated Python SDK, followed by a fresh current-user, cluster-list, and warehouse-list validation through the normal resolver. Authentication, workspace-network, permission, argument, and unknown failures do not trigger provider cycling.

The resolver passes its validated absolute SDK interpreter to the adapter. Direct SDK calls also use Anvil's persisted provider inventory, so a clean process does not lose an SDK installed or discovered outside a default path. A successful fallback is saved as the selected provider; failed validation leaves an existing profile in place and not READY.

Cluster and warehouse probes now use the dedicated metadata-list timeout class. Its 45-second budget is unchanged; this release does not address the reported CLI timeout by simply increasing the limit. If both providers are blocked by the workspace or authentication dependency, readiness remains NOT_READY with the shared blocker.

## Runtime compatibility

The release preserves supported OpenCode 1.x and OpenCode 2.x installations. `make upgrade` continues to preserve the exact validated OpenCode executable and version; use `make update-runtime` for an explicit same-major runtime update. The Databricks changes do not require OpenCode 2.

## Version choice and verification

This is a PATCH release because it fixes provider recovery and executable-path reuse without changing public commands or persisted data formats. No migration is required. Offline regression tests cover the installed-CLI timeout, successful SDK provisioning and fallback, blocked SDK installation, stop-on-shared-failure behavior, the metadata timeout class, and clean-process SDK discovery and execution. No live workspace smoke test was run. Network required for `make upgrade`: NO; explicit setup may use the configured package source when it needs to install the SDK fallback.
