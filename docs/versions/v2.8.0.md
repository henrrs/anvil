# Anvil 2.8.0 — Lifecycle and State Migration Hardening

Anvil 2.8.0 makes lifecycle state explicit and makes configuration ownership verifiable. It addresses the 2.6.x-to-2.7.0 profile deadlock by validating an installed profile as the source release that created it, then planning the transition to the checkout release.

## Lifecycle behavior

`make inspect` reports `READY`, `STALE`, `MIGRATION_REQUIRED`, `DEGRADED`, `CORRUPTED`, `UNSUPPORTED`, or `RECOVERY_REQUIRED` without modifying state. `STALE` means a compatible earlier patch release; `MIGRATION_REQUIRED` means a supported earlier minor. `make doctor` reports source validity and the available upgrade path. An installation is eligible for automatic Anvil migration when it is from the same product major and within the current plus two previous minor releases. A checkout older than the installed Anvil release is never allowed to downgrade it.

Both `make upgrade` and `make reforge` refuse to run from a checkout older than the installed Anvil release. If a machine has a newer installation than the checked-out repository, switch to that release or a newer checkout before retrying; reforge is not a downgrade or cross-release recovery path.

`make upgrade DRY_RUN=1` stages the same source-to-target plan as a real Anvil upgrade, verifies the candidate config and rehearsal, and reports managed-file additions, updates, removals, preserved user files, and the exact runtime preservation action. It does not create a live snapshot, stop OpenCode, write the lifecycle journal, or change live configuration. A user-owned file that collides with a newly managed target path blocks before confirmation or mutation.

Real lifecycle changes verify a snapshot, write a durable transaction journal, then atomically stage and activate the configuration. Installation metadata records the manifest checksum only after configuration activation. If the process is interrupted, `make inspect` reports `RECOVERY_REQUIRED`; rerunning the lifecycle command after closing OpenCode restores the verified snapshot and retries. `make rollback` performs that recovery and exits after restoring the interrupted operation's snapshot.

Reforge remains the explicit reconstruction path. It preserves user-owned extra files and CLI/TUI preferences. If a manifest-backed Anvil file is missing or changed, reforge can rebuild it from this checkout while retaining files that the manifest identifies as user-owned. An unreadable or untrusted manifest still requires manual review.

The release-owned skill/command inventory records the Anvil version that introduced each capability. Inline user agents disabled in the source profile are preserved across V1/V2 rebuilds; Anvil-owned agents are reconciled from manifest metadata. Upgrade preflight also requires a writable config parent before stopping OpenCode or creating a snapshot, so a read-only XDG config directory fails without leaving a transaction behind.

## Runtime compatibility

Anvil-only `make upgrade` preserves the exact validated OpenCode executable, version, data, and state. Same-major `make update-runtime` keeps the installed Anvil release and config intact. `make migrate-runtime OPENCODE_MAJOR=N` requires Anvil to be current because it changes the OpenCode config adapter. OpenCode 1.x and 2.x remain supported; no runtime upgrade is required for this Anvil release.

## Migration

From Anvil 2.6.x or 2.7.x, run:

```sh
make inspect
make upgrade DRY_RUN=1
make upgrade
make doctor
```

Review preserved user files and move any reported collision before rerunning. See the [2.7.1-to-2.8.0 migration guide](../migrations/v2.7.1-to-v2.8.0.md), [public command contract](../command-contracts.md), and [ADR-0016](../decisions/ADR-0016-lifecycle-state-and-managed-file-migration.md).

Network required: no for `make upgrade`. Runtime release lookup remains limited to explicit runtime update/migration or first-install provisioning.
