# Anvil 2.5.0 — Anvil-Owned Databricks Configuration

Anvil 2.5.0 is a MINOR release. It replaces external-profile reuse with a clean Anvil-owned Databricks config and profile. It keeps the existing `make databricks-setup` command and provider state schema, and does not require an OpenCode 2 runtime.

## Clean Anvil profile

`make databricks-setup` asks for a Databricks workspace URL and neutral environment label, then creates `anvil-dev`, `anvil-staging`, `anvil-prod`, or a custom `anvil-*` profile in `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks/databrickscfg`. The CLI and SDK use this same config path and profile. Anvil never adopts, changes, or reauthenticates an external profile. Legacy profile names are ignored; a saved host is offered only as a user-confirmed workspace suggestion.

The staged profile is validated through current-user identity before it is activated. Writes are atomic, the config is mode `0600` in a mode `0700` directory, and provider state contains ownership/authentication metadata but no credentials. `make databricks-setup RESET=1` replaces only owned config after validation and retains a private backup. Healthy Anvil setup is idempotent.

## Authentication and environment

Authentication is selected after workspace, cloud, topology, providers, and Azure session status are known. Existing Azure CLI sessions can be reused. Local Azure sessions use Azure CLI interactive login; remote Azure sessions can use device code. Databricks CLI OAuth U2M remains an appropriate local fallback. Remote/headless contexts do not assume a browser loopback callback. Anvil strips inherited `DATABRICKS_*` variables from child environments and reports conflict names only.

The CLI and SDK share Anvil's Unified Authentication profile. SQL Connector remains a specialized OAuth U2M path because it does not consume the shared SDK profile; it is not substituted for Azure CLI authentication. External profiles are reported separately by doctor and are never used by Anvil.

## Migration from 2.4.0

See the [2.4.0-to-2.5.0 migration guide](../migrations/v2.4.0-to-v2.5.0.md). Existing external profiles and cloud CLI sessions remain in place. A user who previously configured Databricks through an external profile may need one clean sign-in for the new Anvil-owned profile; Anvil does not copy credentials.

## Compatibility and validation

Anvil 2.5.0 keeps both OpenCode 1.x and OpenCode 2.x runtime profiles, the existing Databricks CLI/SDK routing, safe lifecycle quiescing, and the explicit runtime-major migration boundary. An Anvil upgrade preserves the exact validated OpenCode executable and version. Use `make update-runtime` only for an explicit same-major runtime update; `make migrate-runtime OPENCODE_MAJOR=N` remains the explicit major transition.

`make test` exercises both runtime profiles and local Databricks/Azure/SDK fakes. Network required: no for mandatory tests; a real workspace smoke check is separate and was not run for this release.

The release does not add an OpenCode 2 requirement, custom OAuth implementation, MCP requirement, external-profile migration, or credential copying.
