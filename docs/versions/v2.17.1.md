# Anvil 2.17.1 — Installed-State Convergence and Recovery

Anvil 2.17.1 is a PATCH release that hardens installed-state convergence and lifecycle recovery. It preserves OpenCode 1.x and 2.x support and the Anvil 2.17 Analytics contracts, including the required DuckDB/PyArrow runtime built from `config/analytics-requirements.lock` with Python 3.11+.

## Convergence and recovery

The Analytics service uses systemd-specific serialization for `WorkingDirectory`, validates candidate units with `systemd-analyze verify` when available, and checks staged interpreters by execution, `sys.prefix`, and required imports. Normal Python venv interpreter symlinks are accepted when their resolved environment is correct. Activation and rollback preserve the active dependency pointer until the previous config and service definition are restored.

The lifecycle journal classifies abandoned pre-activation staging, interrupted activation/restoration, committed-but-unfinalized upgrades, and unknown states. Recovery verifies the captured baseline before repeating rollback; it finalizes a committed target when the installation record and managed manifest prove it is already active. Unknown journals block while preserving the snapshot.

OpenCode health probes use a short per-attempt timeout within a bounded startup deadline. A failed persisted URL invalidates its adapter before startup retry, allowing the canonical Analytics session to be reused or recovered on a live runtime.

Each SQLite control-store migration declares a rollback policy such as `BACKWARD_COMPATIBLE`, `BACKUP_RESTORE_REQUIRED` or `NON_ROLLBACKABLE`. Incompatible transitions require a verified consistent SQLite backup before activation; restoration occurs only for that policy and precedes baseline service startup. Local datasets and Parquet materializations are not copied. Unknown or non-rollbackable transitions block before activation.

The release inventory is checked against the actual deployed artifact set. Production upgrade preflight rejects release-owned working-tree changes before snapshot or dependency staging. Host-side lifecycle tools remain outside the managed config manifest. Corporate package sources are selected without rewriting pip configuration or collecting credentials from unrelated tools; observable network failures receive registry/network classifications.

## Compatibility and verification boundary

Both OpenCode 1 and OpenCode 2 keep the same Analytics provider, loopback service and canonical Analytics session contracts. Unity Catalog metadata hydration and warehouse lifecycle behavior are unchanged. The existing 1366×768, 1920×1080, 2560×1440 and 3840×2160 workspace geometry coverage remains applicable.

The engineering report records which offline regressions passed. Offline fixtures do not establish access to a live Unity Catalog, corporate package registry, real systemd user manager, live OpenCode model, or Windows-to-WSL browser forwarding. Network required for `make upgrade DRY_RUN=1`: **NO**.
