# Anvil 2.18.0 — Analytics Correctness and Recovery

Anvil 2.18.0 strengthens the default Analytics workspace without changing supported OpenCode 1.x/2.x runtime floors, DuckDB/PyArrow pins in `config/analytics-requirements.lock`, or the SQLite schema. Existing installations can use `make upgrade DRY_RUN=1` followed by `make upgrade`; it is an Anvil-only upgrade. Python 3.11+ remains required. Unity Catalog access and warehouse usage remain optional remote capabilities. The same-major automatic migration window now covers twelve prior minor releases, retaining the supported 2.6.x source line.

## Analytics query correctness

LOCAL and AUTO now derive bounded `QueryRequirements` and check local coverage before remote warehouse discovery. Covered queries use DuckDB without Databricks calls; AUTO selects Databricks only when local coverage cannot prove the request. Aggregates, grouping, distinctness, ordering and limits are evaluated by DuckDB from the original query. Local dataset readiness requires agreement among coverage metadata, physical Parquet schema and DuckDB-visible schema. Mismatched data is marked invalid; an unavailable independent schema reader does not produce a false READY state.

## Materialization recovery

Workers persist process identity, start time and heartbeat leases. Startup reconciliation marks abandoned operations failed and cleans only their staging generation, preserving CURRENT. One process-held lock serializes writers and local-copy removal for a workspace/table. Retry creates a fresh operation ID and plan; persisted chunks are never resumed across processes. The UI reports phase, start and last activity and offers retry for terminal failures. Cancellation accepts a no-body action and preserves CURRENT.

## Databricks service trust and API behavior

The managed Analytics service receives only readable CA path variables from an explicit allowlist. Fallback startup no longer copies the complete shell environment. Databricks status reports configuration, authentication, TLS trust, workspace and warehouse discovery separately; local SQL remains independent. Local-copy deletion uses DELETE, no-body cancel/retry actions are accepted, form validation is shown in the dialog, and all-column selection has no generic confirmation.

## Ask Anvil

The logical `anvil-analytics` policy prefers Luna 6 through GitHub Copilot. Each prompt validates the connected provider and matching model from the runtime `/provider` catalog and dispatches the exact IDs returned there. Catalog discovery has a larger route-specific response ceiling; ordinary runtime requests keep their existing bound. Provider discovery, unavailable provider and missing model errors remain distinct, and no invalid fallback is used. The canonical Analytics session remains reused.

## Compatibility and validation boundary

Both supported runtime generations keep the same public Analytics capability contract. The offline suite exercises local fakes and does not certify a live Databricks workspace or a live GitHub Copilot account/model. In this development environment the CLI lists OpenAI as authenticated and does not recognize GitHub Copilot, so live preferred-provider certification is not available here. Native dependency behavior is reported only if the managed DuckDB/PyArrow runtime is present. The responsive workspace remains covered at 1366×768, 1920×1080, 2560×1440 and 3840×2160.

Network required for `make upgrade DRY_RUN=1`: **NO**. No database or Anvil persistent-state migration is required.
