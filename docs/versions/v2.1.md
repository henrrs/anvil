# Anvil 2.1.0 — Runtime Independence

## Release objective

Anvil 2.1 separates the Anvil release from the OpenCode runtime generation. Anvil 2.0 installed OpenCode 2 during normal upgrades, which made the product unavailable to teams that could not approve or install that runtime. Anvil 2.1 supports OpenCode 1.x and 2.x through small runtime profiles while keeping commands, skills, Markdown memory, and source workflows common.

> Anvil upgrades Anvil. Runtime migration upgrades the runtime.

## Runtime policy and adapters

`config/runtime-policy.json` lists supported runtime majors, a default major for first installation, minimum supported versions, and the automatic-major-upgrade rule. The current policy supports OpenCode 1.x from `1.18.18` and OpenCode 2.x from `2.0.0`; first installs default to OpenCode 1. The policy default is not an upstream-latest declaration and does not change an existing installation's selected major.

The `opencode-v1` and `opencode-v2` profiles render native configuration for each runtime. `scripts/runtime.py` centralizes version inspection and the capabilities surfaced to operations. Shared Anvil files remain shared. The OpenCode 2 plugin, native References, ordered permissions, bounded tool output, and structured stats are enabled only where the selected runtime provides them.

Use `make capabilities` to see the detected profile and fallbacks. `FORMAT=json make capabilities` emits a machine-readable capability record. Capabilities describe the runtime currently selected; they do not pin a model or change runtime policy.

## Lifecycle behavior

### `make reforge`

Reforge builds a clean managed configuration and stages the latest supported release within the current runtime major. On first installation, it uses `default_major` from runtime policy. A reforge therefore does not jump from OpenCode 1 to OpenCode 2 because a newer major exists upstream.

### `make upgrade`

Upgrade updates the Anvil configuration and runtime patch/minor candidate while preserving the installed OpenCode major. For example, OpenCode 1 remains OpenCode 1. The command stages one exact candidate, builds the matching adapter config, rehearses against copies of config/data/state/memory, verifies a complete backup, installs the rehearsed candidate, runs doctor, and rolls back if postflight fails.

`make upgrade DRY_RUN=1` performs the preflight and isolated rehearsal, then exits before creating a live backup or changing user files. It reports the selected adapter, candidate, and feature profile.

### `make migrate-runtime`

An OpenCode major change is explicit:

```bash
make migrate-runtime OPENCODE_MAJOR=2
```

The requested major must be supported and must differ from the installed one. Migration uses the same candidate staging, config audit, copied-state rehearsal, verified backup, postflight doctor, and rollback path as an upgrade. Use `DRY_RUN=1` to inspect and rehearse it first. The OpenCode 1 reverse adapter is also available with `OPENCODE_MAJOR=1`.

Anvil archives OpenCode data and state as opaque files. Rehearsal starts the candidate against copied state through that runtime's native stats command. It does not query or edit undocumented database tables and it does not make a provider/model request.

## Memory V2 and source evidence

Persistent memory remains portable Markdown. Existing entries remain readable; aliases, status, evidence, and richer source provenance are optional. The supported status vocabulary is `sourced`, `corroborated`, `conflicted`, `historical`, and `uncertain`. Confidence remains a small qualitative value. Search stays lexical, accent-insensitive, bounded, and standard-library capable when `rg` is absent.

`/remember` remains explicit and duplicate-aware. `/recall` shows relevant status, confidence, aliases, evidence, and provenance. When a linked registered source changed or disappeared, recall marks the memory as potentially stale. That warning is non-destructive; it asks the agent to recheck evidence instead of rewriting memory.

`/distill` remains runtime-independent. It processes only sources named by the user, synthesizes claims instead of fixed-size chunks, checks useful documentation/code/tests/configuration/Git evidence, separates normative guidance from current implementation, and retains meaningful conflicts or historical status. The atomic source registry hashes named local files and skips unchanged sources. Changed sources are surfaced for reconciliation; knowledge files are never edited by distillation.

## Runtime-specific capability fallbacks

| Capability | OpenCode 1 profile | OpenCode 2 profile |
|---|---|---|
| Commands and skills | Native Markdown discovery | Native Markdown discovery |
| Memory search | Installed Python file helper | Same helper plus the bounded read-only `anvil_memory_search` plugin tool |
| Knowledge | Ordinary reads of explicitly named files under the Anvil knowledge directory | The `anvil-knowledge` Reference plus ordinary file reads |
| Stats | OpenCode's native text report | OpenCode's structured JSON report, formatted by Anvil |
| Permission config | Singular V1 schema; one agent, deny-by-default, no task tool | Ordered native permission rules; one agent, deny subagents |
| Compaction | OpenCode 1 native compaction settings | OpenCode 2 native compaction settings |

`make stats` prints the native report for the current runtime. If it cannot be obtained, Anvil reports that it is unavailable and does not invent token or cost values. No separate telemetry database is introduced.

## Doctor and project overrides

`make doctor` reports the Anvil release, OpenCode version/profile, policy major, configuration and agent health, memory and source-registry validity/drift, runtime capabilities, migration metadata, and visible project overrides. It does not delete project-owned instructions, skills, plugins, or MCP settings. A healthy older Anvil installation is shown as `UPGRADE AVAILABLE` rather than blocked from using the existing runtime.

## Migration path

For an existing Anvil 2.0 installation on OpenCode 2, run `make upgrade`; it stays on OpenCode 2. For a supported Anvil V1 installation on OpenCode 1, run `make upgrade`; it updates Anvil while remaining on OpenCode 1. See [2.0 to 2.1 migration](../migrations/v2-to-v2.1.md) and [runtime compatibility](../runtime-compatibility.md).

## Known limitations

- OpenCode 1 does not expose Anvil's native plugin tool or OpenCode 2 Reference API. Anvil uses the file-search and direct-read fallbacks.
- OpenCode 1 stats are native terminal text rather than the structured JSON Anvil can normalize on OpenCode 2.
- Runtime installers need access to the official GitHub release endpoint for OpenCode 1 or the official npm registry for OpenCode 2. The candidate is verified against the digest published by its release source.
- Company-managed OpenCode policies, project config, or system configuration may alter effective runtime behavior outside Anvil's global config. Doctor reports visible overrides but does not remove them.
- Semantic distillation quality remains agent-guided; deterministic tests cover provenance, idempotency, freshness and reconciliation fixtures, not LLM judgment quality.

## Non-goals

Anvil 2.1 does not add multi-agent orchestration, model routing, automatic memory capture, background source crawling, embeddings, vector search, an external memory service, a telemetry database, or a hard dependency on OpenCode 2.

## Rollback

`make rollback` restores the complete verified pre-upgrade or pre-migration OpenCode config, managed runtime, data and state snapshot. Current Anvil Markdown memory remains portable and is archived separately before rollback. OpenCode databases are restored as opaque files; Anvil does not try to downgrade their schemas.
