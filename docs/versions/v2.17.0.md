# Anvil 2.17.0 — Analytics Runtime and Workspace Hardening

Anvil 2.17.0 makes new and existing Analytics installations converge on the same supported runtime while preserving OpenCode 1.x/2.x independence. The default Analytics feature remains outside traditional Anvil core dependencies.

The same-major migration source window now covers eleven prior minor releases, retaining the previously supported Anvil 2.6.x line.

## Runtime convergence

`config/analytics-requirements.lock` binds DuckDB 1.5.5 and PyArrow 26.0.0 to this Anvil release. Anvil prepares an isolated Python 3.11+ environment under its XDG data root, keyed by Python minor version and the lockfile digest. The service uses that exact interpreter and validates both imports and versions before publishing the environment. Failed preparation retains the previous supported runtime and prevents config activation.

Fresh reforge, `make upgrade`, `make update-runtime`, and `make migrate-runtime OPENCODE_MAJOR=N` prepare dependencies and install required runtime artifacts. Runtime migrations defer service activation until the requested OpenCode executable is installed. Lifecycle completion requires a managed service health response, OpenCode runtime readiness, and a valid canonical Analytics session. `make upgrade DRY_RUN=1` reports dependency, artifact, service, runtime/session, and catalog-refresh actions without changing local state.

## Service and readiness

The managed service reports installation, unit enablement, active state, MainPID and HTTP health separately. A zero MainPID cannot be READY. `make analytics` idempotently reuses or starts the one managed service and prints its URL. Systems without a user systemd manager use an Anvil-owned PID/lock managed process. `make analytics-dev` is the explicit foreground development mode. Systemd paths use directive-specific escaping and are regression-tested with `systemd-analyze verify`.

Inspect, doctor, capabilities and `/api/runtime` consume the same structured local readiness response for the service, OpenCode/canonical session, required dependencies and cached catalog. Doctor warns when an installed default Analytics capability is degraded and reports `make upgrade` as the dependency recovery path.

## Catalog and warehouse lifecycle

Unity Catalog discovery now refreshes catalogs, schemas and tables/views into SQLite in bounded background phases, displays cached metadata first, records per-scope state and overall progress, and reconciles removed objects. The root cause of missing table metadata was a table-list page size larger than the documented API maximum: Anvil now requests up to 50 rows and follows every page token. Metadata provider concurrency is capped at two. Permission/provider failure remains distinct from a confirmed empty scope; rows and column detail stay lazy.

Remote SQL starts an explicitly selected STOPPED warehouse once, waits through STARTING/STOPPING, and returns actionable permission and timeout errors. The lifecycle is invoked only after query routing resolves to Databricks; LOCAL and AUTO-to-LOCAL never start compute.

## Query workspace

The SQL editor/results divider is pointer- and keyboard-operable, announces its orientation/value as a separator, preserves a bounded ratio in browser-local storage, maintains minimum pane heights and triggers editor reflow. Full frontend geometry, drag, keyboard and reload persistence are certified at 1366×768, 1920×1080, 2560×1440 and 3840×2160.

## Upgrade

```bash
make upgrade DRY_RUN=1
make upgrade
make inspect
make doctor
make capabilities
make analytics-status
```

If a required wheel cannot be fetched or validated, the lifecycle fails before config activation and leaves the previous supported installation available. Configure the existing Python package mirror/proxy and retry; do not install into system Python manually. The [migration guide](../migrations/v2.16.0-to-v2.17.0.md) describes the safe update sequence.

## Evidence and limits

The [engineering report](../analytics-workspace-report-v2.17.0.md) records root causes, implementation boundaries, tests, screenshots and limitations. The deterministic suite uses fake Databricks/OpenCode providers and isolated state; it does not establish real workspace permissions, real package-mirror access, a real systemd user session, live OpenCode model quality, or Windows-to-WSL browser reachability. Network required for `make upgrade DRY_RUN=1`: **NO**.
