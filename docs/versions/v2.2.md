# Anvil 2.2.0 — Execution Intelligence

## Release objective

Anvil 2.2 improves the single-agent operating contract and adds an optional Databricks capability that works with supported OpenCode 1.x and 2.x runtimes. The release theme is **Execution Intelligence**: forge more intelligence from every token. The Databricks capability uses the official CLI and REST APIs through common shell and filesystem primitives; it does not require a model change, OpenCode migration, MCP, or a Python SDK.

## Harness changes

The global `config/AGENTS.md` was reorganized into hard invariants and flexible operating guidance. It preserves the Understand → Locate evidence → Form a hypothesis → Act → Verify → Finish loop, adds an evidence-sufficiency transition, and directs failure recovery to classify the failure and change an assumption or method before retrying. It strengthens validation, task scope, data minimization, and Databricks mutation and cost-claim constraints. Databricks vendor schemas remain in the lazy skill references rather than the global harness.

| Harness size | Bytes | Approximate tokens* | Change |
|---|---:|---:|---:|
| Anvil 2.1 `AGENTS.md` | 4,790 | 1,198 | Baseline |
| Anvil 2.2 `AGENTS.md` | 3,710 | 928 | 22.5% fewer bytes |

\*Approximate token count is UTF-8 bytes divided by four. It is a sizing estimate, not a tokenizer measurement. The offline test enforces a 4,200-byte ceiling and required invariant phrases. No behavioral benchmark was run, so this release makes no measured model-performance claim.

Skills were kept focused; each description now says when it applies and when it does not. The Databricks skill uses progressive disclosure across authentication, compute, SQL warehouses, system tables, FinOps, and seven SQL recipes.

## Databricks architecture and authentication

The installed `scripts/databricks.py` adapter centralizes CLI discovery, profile validation, REST requests, SQL/Python execution, bounds, and error categories. The optional `databricks_finops.py` module computes evidence quality and conservative workload findings. The entry skill is shared by both OpenCode profiles.

Anvil supports Databricks CLI `1.0.0` or newer. This minimum was selected from current official CLI/auth guidance; CLI 1.0.0 introduced OS-native secure storage for OAuth U2M tokens. The CLI remains the credential owner. Anvil never reads sensitive auth output or persists tokens, passwords, or client secrets. Setup validates with `auth profiles`, non-sensitive `auth describe`, and `current-user me`.

Anvil stores the selected default profile, HTTPS workspace host, schema version, and verification time in `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks.json`, mode `0600` under a `0700` directory. One valid profile can be selected automatically. Multiple profiles require user choice. A missing or invalid selected profile triggers repair guidance; it is not replaced by another profile. Commands may name a profile explicitly without overwriting the saved default. These preferences are outside the OpenCode config backup tree and remain separate from OpenCode runtime state.

`make reforge` and `make upgrade` offer optional interactive configuration when a terminal is available. Missing CLI, missing authentication, or failed optional Databricks setup does not prevent Anvil installation. `make databricks-setup` is the single setup/recovery command.

## Compute and execution

For requested remote Python, the adapter discovers accessible running classic all-purpose clusters and filters job/pipeline compute. It reports IDs, names, state, source, runtime, worker/driver types, and worker ranges. A user must choose among multiple running clusters. If only stopped clusters exist, Anvil asks before any start; the adapter itself has no start, restart, resize, edit, or terminate operation. Python runs through the Command Execution API with a created context, bounded polling, bounded returned output, timeout cancellation, and context destruction in `finally`.

For requested SQL, Anvil discovers SQL warehouses and uses the Statement Execution API. A user chooses when several are running. Stopped warehouses require approval before a start, and the adapter has no warehouse mutation operation. Inline JSON results are capped at 100 rows and 1 MB; polling distinguishes pending/running from success, failure, cancellation, and timeout. Common write and configuration statements are blocked unless direct user approval is represented explicitly to the adapter.

Remote execution is only appropriate when the user's request clearly asks for it. Generated Python is reviewed for destructive or externally visible effects. Query values should use statement parameters. Operational data is filtered and aggregated in Databricks before it enters model context.

## System-table snapshot and live authority

The skill ships a dated snapshot of the current official system-table catalog checked on 2026-10-16. For each listed table or documented family, the index records its purpose, availability marker (GA/unmarked, Public Preview, or Beta), retention, and regional/global scope; focused pages cover billing, compute, Lakeflow, query history, warehouses/events, lineage, and other current schemas. Source links point to the official catalog and schema pages.

The snapshot is an index for progressive discovery, not an availability guarantee. Before relying on a table, Anvil should use bounded live `SHOW SCHEMAS`, `SHOW TABLES`, or `DESCRIBE TABLE` when practical. Live grants, region, cloud, account enablement, preview state, schema, configured retention, and delivery lag win for the active task. System tables are read-only and can contain sensitive operational data; raw rows do not enter Anvil memory by default.

## FinOps methodology

The seven SQL recipes cover job run summaries, job cost, classic cluster utilization/sizing, warehouse activity/cost, and query performance. Recipes use time-window parameters, aggregate near the source, cap result sets, and keep Databricks system tables read-only. Job-run timeline slices are aggregated by workspace/job/run identity before counting or timing runs. Billing price joins use the effective list price at the usage timestamp. Dedicated/serverless attribution is distinguished from approximate shared all-purpose allocation. Databricks usage/list cost is never presented as a complete cloud bill.

The deterministic Evidence Confidence Score is a 0–100 **evidence quality** score, not a probability of success:

| Dimension | Points |
|---|---:|
| Sample sufficiency | 4 / 8 / 14 / 20 based on fewer than 5, 5–9, 10–19, or at least 20 runs |
| Telemetry coverage | `round(20 × coverage)` |
| Freshness | 15 (≤24 h), 11 (≤7 days), 6 (≤30 days), otherwise 0 |
| Cost attribution | 15 dedicated/serverless/warehouse; 4 shared; 8 unknown/other |
| Independent signal agreement | 4 per distinct signal, capped at 15 |
| Configuration history | 15 complete; 8 partial; 0 missing |

Penalties are −30 for unavailable system-table access, −8 for fewer than three runs, −10 for coverage below 50%, −10 for short-lived compute, −10 for partial/stale billing, and −15 for conflicting signals. The result is clamped to 0–100; LOW is below 55, MEDIUM is 55–79, HIGH is 80 or above. Strong classic-compute recommendations require repeated runs, good telemetry coverage, low p95 CPU/memory and wait, ample worker headroom, historical configuration, and sufficiently precise cost attribution. High peaks block aggressive downsizing. Weaker evidence yields a controlled test candidate or no conclusion.

## Offline validation

`make test` no longer resolves or downloads OpenCode candidates. Local OpenCode fixtures validate OpenCode 1/2 config discovery; the fake Databricks CLI supplies auth, resource, API-state, permission, and system-table fixtures. Deterministic tests cover profile permissions and persistence, multiple profiles, invalid-profile non-switching, compute/warehouse selection, Python cleanup and cancellation, SQL bounds and mutation rejection, live-schema fixture responses, FinOps scenarios, and SQL recipe contracts. It also checks the harness budget/invariants, all skill descriptions, runtime independence, combined capabilities JSON, and tracked/untracked text for the standalone legacy identifier.

The tested cases include strong underutilization, low averages with high peaks, shared compute, incomplete telemetry, SQL warehouses, missing system-table permission, several clusters/warehouses, and stopped compute. No test calls a model or Databricks workspace. This suite verifies offline contracts; it does not claim a live service connection.

## Runtime compatibility

Anvil 2.2 supports OpenCode 1.x from `1.18.18` and OpenCode 2.x from `2.0.0`, retaining the existing runtime policy and explicit migration command. Offline profile fixtures validate both. Databricks uses the same installed scripts and skill on each runtime. No Databricks operation requires an OpenCode 2 plugin, OpenCode 2-only permission, or MCP.

## Security and operational limits

- Credentials stay in Databricks CLI authentication storage. Logs omit raw command output, SQL text, Python code, tokens, identity payloads, and result rows.
- No cluster, warehouse, workload, permission, or system-schema mutation is offered by the adapter. No stopped resource is started automatically.
- SQL and returned command output are bounded. SQL mutation screening is conservative lexical protection and is not a substitute for the user's approval or workspace permissions.
- Databricks installation and authentication are optional. A `make doctor` report can show Databricks as not configured without making the Anvil installation unhealthy.
- The system-table snapshot can age; live workspace metadata and schemas are authoritative.
- The 2.2 suite has no live OpenCode candidate or Databricks smoke run. Runtime release installation still requires network access to official artifact sources.

## Upgrade, rollback, and non-goals

Use `make upgrade DRY_RUN=1` to stage and rehearse the Anvil 2.2 change, then `make upgrade` to apply it. The installed OpenCode major is preserved. Existing memory stays in its separate user data directory. Databricks CLI profiles and Anvil Databricks preferences are not rewritten by upgrade. `make rollback` restores the verified OpenCode config/runtime/data/state snapshot and leaves the separately managed Databricks profile preferences in place.

Anvil 2.2 does not add multi-agent orchestration, model routing, vector search, automatic memory writes, a Databricks Python SDK dependency, MCP, a telemetry database, or an OpenCode major migration.

For operational detail, see [Databricks documentation](../databricks/README.md), [runtime compatibility](../runtime-compatibility.md), and the [2.1-to-2.2 migration guide](../migrations/v2.1-to-v2.2.md).
