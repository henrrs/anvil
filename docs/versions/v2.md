# Anvil 2.0.0 — V2

## Overview

Anvil 2.0.0 moves the managed runtime to OpenCode 2 while keeping Anvil a lean, model-agnostic harness. OpenCode owns provider selection, models, authentication, sessions, execution tools, its database, and native compaction. Anvil owns the shared instructions, one primary agent, allowlisted skills, explicit Markdown memory, a small read-only memory-search plugin, and safe lifecycle operations.

## Goals

Preserve V1's useful single-agent and explicit-memory behavior. Add only the migration safety, knowledge reuse, provenance, and runtime visibility needed for a dependable V2 release.

## What changed from V1

- OpenCode's native V2 config keys and ordered permission rules replace V1's singular config schema.
- `make upgrade` rehearses V1 state in an isolated HOME/XDG environment, backs up the complete live runtime snapshot, installs the exact candidate that passed rehearsal, and rolls back after post-mutation failure.
- `make reforge` remains a clean baseline rebuild and first-install path.
- Rollback restores the saved config, binary, OpenCode data, and OpenCode state. Anvil Markdown memory remains portable and is archived before rollback.
- Installation records now include Anvil/OpenCode versions, release artifact integrity metadata, and migration history.

## New capabilities

### `anvil-core` and memory search

The local OpenCode 2 plugin registers one bounded `anvil_memory_search` tool. It uses the installed Markdown helper for lexical search, limits returned entries/excerpts, and does not write memory. It adds no hooks, prompt rewriting, provider/model routing, or automatic memory harvest.

### Memory V2

V1 Markdown entries remain readable and searchable. New optional fields include aliases, status, evidence, section, line range, repository, and SHA-256 provenance. Search normalizes Unicode accents and falls back to Python when `rg` is absent. Persistent writes still require explicit `/remember` or `/distill` authorization.

### `/distill` and evidence reconciliation

`/distill` works only on sources the user names. It synthesizes a small set of reusable claims rather than chunking documents. It asks the agent to check active code paths, imports, tests, configuration, and relevant history; retain provenance; separate normative policy from implementation behavior; surface conflicts and drift; ignore unreferenced old code as current truth; and label historical material. Uninspected images are not treated as evidence.

For local files, a private source registry records stable source identity, current SHA-256, Git provenance when available, timestamps, and linked memory IDs. An unchanged-source plan returns a zero-write skip result. Changed sources are reported for review and re-distillation.

### Knowledge References, stats, and doctor

The `anvil-knowledge` Reference points to a separate user data directory and is not the memory store. `make stats` formats OpenCode's native JSON usage report without adding telemetry storage. V2 doctor checks the managed config, agent permissions, commands, skills, plugin runtime, memory validity, knowledge root, source registry, migration metadata, and current workspace overrides.

## Upgrade model

`make upgrade` resolves the npm `latest` tag for the official `@opencode/cli`, requires an exact stable 2.x.y version, verifies the platform package's SHA-512 integrity, and stages one candidate. The rehearsal copies the current global config, OpenCode data/state directories, and Anvil Markdown memory into a private temporary HOME/XDG tree. It builds the V2 config, runs OpenCode 2 against the copied state using native stats, and checks that the actual candidate loads Anvil's agent, commands, skills, plugin, and Reference.

Only after rehearsal and a verified backup does the live replacement begin. OpenCode must be closed so its opaque database files are stable while being copied. A failed postflight restores the verified pre-upgrade snapshot.

## Backward compatibility

- Existing V1 memory files are not rewritten by upgrade or rollback.
- Custom provider definitions are mapped into the V2 provider structure; CLI/TUI config files are retained for OpenCode's native migration behavior.
- OpenCode databases are treated as opaque artifacts. Anvil does not inspect or edit their internal SQLite schema.
- Rollback restores the old runtime and config snapshot, while current Anvil memory remains at its data path and is separately archived.

## Known limitations

- OpenCode 2 migration can be influenced by managed, system, project, or environment configuration outside Anvil's user-global tree; doctor reports visible project overrides but cannot remove them.
- The rehearsal exercises native V2 server/API and stats startup on copied state. It does not open an interactive TUI or verify the rendered terminal UI.
- Provider authentication is copied as opaque state and is not used to make a model request during the rehearsal.
- A V1 installation without Anvil release metadata is labeled `V1 (version not recorded)` in the backup rather than assigned an invented version.
- Source distillation is agent-guided. The source registry and tests make provenance and skip behavior deterministic, but tests do not claim to evaluate semantic quality of an LLM synthesis.

## Explicit non-goals

V2 does not add multi-agent orchestration, model routing, vector search, a RAG service, automatic memory extraction, background source crawling, cost controls, or a separate telemetry database.

## Rollback

Run `make rollback` to restore the latest verified pre-upgrade/rebuild config, installer tree, OpenCode data, and OpenCode state snapshot. Rollback does not remove V2 Markdown memory; it archives the current memory before restoring the former runtime.
