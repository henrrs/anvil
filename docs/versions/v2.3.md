# Anvil 2.3.0 — Databricks Provider Independence

## Release objective

Anvil 2.3 removes the accidental assumption that the Databricks CLI is the only way Anvil can reach Databricks. Anvil integrates with capabilities, then selects a provider for each capability. The CLI remains the preferred general provider when healthy; the official Python SDK is the primary headless fallback.

This release preserves Anvil 2.2's model-neutral single-agent harness, Databricks execution bounds, explicit mutation checks, and OpenCode 1/2 support. It does not require an OpenCode migration, MCP, a Databricks agent, or model routing.

## Harness size

The global harness remains under the 4,200-byte limit:

| Release | `AGENTS.md` bytes | Estimated tokens |
|---|---:|---:|
| Anvil 2.2 | 3,710 | 928 |
| Anvil 2.3 | 3,724 | 931 |

## Explicit Databricks setup

`make databricks-setup` now means “configure Databricks for Anvil.” It validates the current environment and attempts a user-local installation of the official Databricks CLI when no supported CLI is usable. The installer obtains the latest supported official GitHub release for Linux/macOS architectures, verifies the archive against its official SHA-256 manifest, validates the executable, and writes only to `$XDG_DATA_HOME/anvil/databricks/bin`. It does not run privileged commands or alter shell startup files.

This install action is confined to explicit Databricks setup. `make reforge` and `make upgrade` neither install Databricks tooling nor probe workspace authentication. The optional setup hint in those lifecycle flows is informational only.

`make databricks-setup DRY_RUN=1` reports local discovery and intended setup actions without network requests, installation, Anvil state writes, shell changes, or authentication changes. Normal setup can be repeated safely; healthy providers and the saved profile are retained.

## Provider architecture and state

The installed `scripts/databricks.py` adapter loads small provider modules from the managed OpenCode config. A pure resolver selects a provider per capability. Provider state is atomic, schema-versioned, and stored in `${XDG_CONFIG_HOME:-$HOME/.config}/anvil/databricks.json`. It migrates the existing 2.2 profile/host record and stores only non-secret metadata such as absolute executable path, package version, provider state, and capability map. Health is revalidated; cached state is not treated as truth.

Provider order:

| Capability | Selection |
|---|---|
| Workspace, compute, warehouse, jobs, pipelines, Bundles | CLI, then SDK for API capabilities |
| Remote Python on running classic all-purpose compute | CLI, then SDK Command Execution, then VS Code assisted |
| SQL/system tables/FinOps | CLI, then SDK Statement Execution, then SQL Connector when connection metadata supports it |
| Spark development/debugging | Databricks Connect, then VS Code assisted |

VS Code is detected through the public `code --list-extensions` mechanism and the official `databricks.databricks` identifier. It can assist with auth, workspace selection and interactive development; Anvil does not use private extension APIs or UI automation. Databricks Connect remains distinct from remote Python execution and is not installed by default.

## Authentication and SDK fallback

The official SDK version `0.141.0` is installed only in Anvil's virtual environment at `$XDG_DATA_HOME/anvil/databricks/venv`. SDK `WorkspaceClient`, workspace, job, pipeline, cluster and warehouse metadata APIs, Command Execution and Statement Execution reuse supported Unified Authentication profiles and environment sources. Metadata lists are bounded. System and global Python packages are not changed. If the CLI install is blocked by network or policy, setup classifies the reason and continues to the SDK fallback.

Profiles are not silently switched. A single valid workspace profile can be selected; multiple valid profiles require an explicit choice. When auth is missing, setup provides supported CLI/VS Code guidance and can be rerun after login. Tokens, passwords, client secrets, signed URLs, identity data and query/source payloads are not written to Anvil state.

## CLI path resilience

CLI discovery checks the last verified absolute path, the current `PATH`, and bounded supported locations. A CLI outside the current shell `PATH` is still usable by its absolute path and is reported as installed, with PATH integration shown separately. Anvil does not edit shell configuration to repair PATH.

## Preserved execution and security behavior

The shared adapter continues to require a running classic all-purpose cluster for remote Python and a running SQL warehouse for SQL. It never starts, stops, restarts, resizes, creates, or edits remote resources. SQL retains the 100-row/1 MB bounds and mutation approval guard. Python contexts are bounded, canceled on timeout when possible, and destroyed. Live system-table metadata takes precedence over the dated reference snapshot; FinOps retains aggregation, cost-attribution caveats, and the Evidence Confidence Score.

## OpenCode compatibility

Anvil 2.3 supports OpenCode 1.x from `1.18.18` and OpenCode 2.x from `2.0.0`, under the existing runtime policy. The provider adapter is shared and has no OpenCode-specific plugin dependency. Offline lifecycle fixtures exercise both profiles.

## Offline validation

The provider suite uses a fake CLI and a local installer archive/checksum, mocked SDK operations, fake public VS Code CLI output, and isolated HOME/XDG/PATH. It covers resolver priority, SDK fallback for compute/Python/SQL, CLI installation classification, absolute-path reuse after PATH changes, VS Code-assisted reporting, state migration/security, setup idempotency, and no-write/no-network dry-run. The mandatory suite makes no Databricks, GitHub, PyPI, OpenCode candidate, OAuth, or model calls. No live workspace validation was run.

## Migration, rollback, limitations and non-goals

For existing 2.2 users, run `git pull`, then `make test`, `make doctor`, and `make capabilities`. Existing selected profile and workspace host are migrated in place on the next explicit setup. No reauthentication is needed when a supported profile remains valid. Run `make databricks-setup` to refresh provider discovery or install the CLI/SDK fallback.

`make rollback` restores Anvil's managed OpenCode configuration, runtime, data and state snapshots according to the existing lifecycle. Provider preferences remain in the Anvil config data tree; rollback does not uninstall the Databricks CLI, remove the SDK environment, delete profiles, log out, or remove the VS Code extension. The isolated SDK environment is separately owned Anvil data and is not removed by rollback.

The real CLI/SDK installation paths and live Databricks API calls were not exercised by the offline suite. SDK/SQL Connector APIs can evolve; SDK is pinned and the official provider docs should be rechecked before future upgrades. The SQL Connector path requires supported warehouse connection metadata and OAuth U2M; Databricks Connect is a separately configured Spark development environment. Corporate policy restrictions are reported, not bypassed.

Anvil 2.3 does not add a Databricks MCP server, new agent, custom OAuth implementation, generalized SaaS plugin framework, Connect installation, model routing, or automatic CLI installation during standard Anvil lifecycle operations.
